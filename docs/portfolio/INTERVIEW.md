# 面试讲解与技术追问

## 90 秒介绍

灵弦是一套以 FPGA 为声音合成核心的数字乐器。十二个压力键输入音符和力度，摇杆调节弯音、颤音；FPGA 完成声部分配、波形或物理弦计算、包络和混音，再输出给 PT8211。HDMI 显示琴键、波形、频谱与李萨如，RGB 对应实体键位。

系统还有配套的电脑和 Android 应用。应用负责导入、转谱和曲谱整理，经 ESP32-S3 的 BLE 或 USB 桥接上传，FPGA 收到完整曲谱后按时间调度。节奏跟练通过目标键与真实压力键匹配，在板端触发声音。

这个项目里最有技术含量的工作是资源调度与验证：在保留独立声部状态的同时共享运算，把逐像素计算移到帧前完成，并从综合网表证明多周期约束适用的端点。最新 HDMI 单屏版本通过了 163 项 RTL 回归和 3 项官方器件模型测试，布局布线后 setup 为 +0.556 ns、hold 为 +0.187 ns。系统有此前的实物演奏记录，最后这一版完成了仿真与 STA，尚未烧录。

讲完后接上本人实际负责的模块。例如“我主要负责 FPGA 逻辑与系统联调”，必须与真实分工相符；不要在回答中替队友认领 PCB 设计。

## 案例一：显示计算如何移出像素路径

**问题。** 同一帧内曲目位置、长度、速度等显示值不需要逐像素重新计算，直接在显示组合逻辑中进行数字转换会重复使用算术与选择逻辑。

**做法。** 帧边界先锁存状态，六个字段共享一个串行 BCD 加三单元，在 F+78 前完成；画布首次使用在 F+61440。渲染器读取预计算结果，原有 RGB/HS/VS/DE 的相位不变。

**验证。** 覆盖 4096 个位置/长度取值及其他字段，执行 245760 次冻结字形比较；仪表盘等价验证比较 4608000 个缩放像素。负向测试故意提前使用结果，要求与冻结参考发生差异，证明契约有检测能力。

**结果。** 综合对照中显示 LUT 从 2514 降至 2326；整机综合 Logic 从 72104 降至 71926，Register 从 34693 增至 34810。最终 P&R Logic 为 72539，setup/hold 为 +0.556/+0.187 ns。综合和布局布线数字不能混作一组比较，详见 [综合对照来源](EVIDENCE.md#显示优化的综合对照)。

源码入口：[instrument_panel_renderer.v](../../fpga/rhythm/rtl/instrument_panel_renderer.v)。实现说明：[DECIMAL_CHANGE.md](../../fpga/rhythm/DECIMAL_CHANGE.md)。

**追问准备：** 为什么不能直接加一拍而不改同步信号？若帧边界与新状态同拍到达，哪份快照生效？提前出现画布会怎样？为什么增加 FF 仍可能减少组合逻辑？

## 案例二：多周期约束为什么需要证明

**问题。** 音频串行输出与内部计算有不同的推进需求。慢更新的数据并不自动意味着路径可以放宽，尤其是控制信号跨入全速模块时。

**做法。** 内部适用状态由共同 CE 控制，审计脚本沿综合网表的跨层连接检查发射与捕获关系。只有证明满足时序契约的端点才加入集合；setup 与 hold 成对设置。寄存器名称、软件操作频率和“按钮很少按”都不能代替证明。

**规模。** 最新审计覆盖 29 个模块、15992 个半速 FF；捕获查询从 1800 项压缩到 633 项，20 个对象集合证明等价，并执行压缩及层级/使能负向检查。最终生效 10 条 multicycle 命令，包括 4 对共同 CE 和 1 对串化停钟复位约束。

**边界。** 集合变短只能证明约束描述压缩，不自动证明工具总运行时间按比例缩短。未证明的全速路径继续接受正常时序检查。最终检查建立、保持、恢复、移除四类结果。

代码入口：[约束生成脚本](../../fpga/rhythm/scripts/prepare_performance_constraints.ps1)、[SDC](../../fpga/rhythm/constraints/v3_hdmi.sdc)、[验收记录](../../fpga/rhythm/VALIDATION.md)。

**追问准备：** setup=2 为什么必须配套 hold？源端偶尔更新为什么还可能需要单周期约束？集合压缩怎样避免通配符覆盖全速寄存器？

## 案例三：为什么按钮闪烁是通信问题

**问题。** 上位机曾直接用“会话忙”禁用操作按钮，自动 STATUS 查询与音频快照周期性占用连接，按钮随查询反复禁用。用户点击落在禁用窗口时没有动作，表现为“按不了”。

**做法。** 分开界面操作意图和传输占用状态。允许用户提出请求，再等待已有事务结束；进入录音或跟练准备时让后台轮询退出竞争。首次操作自动查询能力，重复点击不重复启动，超时、拒绝和断线明确反馈。设备开始与否以真实 FPGA 回包为准。

**验证。** 页面测试使用显式模拟的延迟 STATUS、拒绝后重试、互斥占用和断线场景，桌面应用检查模式切换与窗口控制。实体联动另用 FPGA 引脚级测试覆盖上传、播放、STOP 后进入跟练，以及 RGB/PT8211 输出。

代码入口：[rhythm-session.js](../../host/instrument-web/src/rhythm-session.js)、[score-upload.js](../../host/instrument-web/src/score-upload.js)、[桥接核心](../../firmware/esp32s3-bridge/main/bridge_core.c)。

**追问准备：** BLE write 返回成功究竟表示什么？环形队列满了怎么办？断线后能否重发 PLAY？语音和上位机同时操作 UART 谁拥有链路？

## 常见技术问题

| 问题 | 回答要点 |
| --- | --- |
| 为什么用 FPGA？ | 独立声部状态、并行数据通路和确定的采样调度适合硬件实现；转谱、网络与复杂 UI 放在应用和 ESP 上。 |
| 共享乘法器后还是 32 复音吗？ | 复音由独立相位、频率、包络和可同时活跃的状态决定；算术单元可以分时复用，但必须在采样期限内完成并避免旧声部结果泄漏。 |
| 同一个音高快速连按如何释放？ | NOTE ON/OFF 按事件身份关联，而不是仅凭音高；检查旧 OFF、新分配与抢占之间的关系。 |
| 12 个实体键为什么要 32 声部？ | 尾音、重复起音与曲谱重奏不等同于当前按住的实体键数；同时说明上传曲谱的准入上限。 |
| 电脑试听为什么与板端不同？ | 转谱存在音符识别误差，板端音色重奏不保留原曲配器；参考试听也不含全部定点舍入和模拟音频链路。 |
| CDC 如何处理？ | 区分单比特控制、稳定多位状态握手及音频数据跨域；解释源端保持、目的端采样和确认，不能把整个多位总线逐位两级同步就视为一致。 |
| 为什么测试多还会有实物问题？ | 事件级注入可能跳过引脚连接、极性、ADC 握手、协议和复位细节。补充引脚级激励与输出解码，硬件兼容性仍需实物验证。 |
| 目前还有什么限制？ | 最后单屏版本未烧录；曲谱 RAM 易失、容量有限；PT8211 非 Philips I²S；转谱不是原声还原。 |

准备时至少亲自读懂一个完整链路：输入条件 → 状态机 → 输出 → 测试断言。能够解释一次取舍及其验证依据，比背诵所有功能更有说服力。
