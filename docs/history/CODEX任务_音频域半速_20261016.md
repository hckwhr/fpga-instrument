# Codex 任务：音频引擎半速化（解决 477 个建立违例）

## 一、换方案的理由

停止逐条拆解时序路径。54g 的 477 个建立违例、setup −3.219 ns，
距门槛 +0.03 ns 差 3.25 ns。按单条路径优化，每轮一次 P&R 约 20 分钟，
且瓶颈会随布局转移（stage29 已验证该现象），时间上不可行。

## 二、核心判断

**全部 477 个建立违例都在 audio_clk 域**（49.1525 MHz，周期 20.345 ns）。

但这个频率只有 `pt8211_tx` 的串行发送真正需要。
`rtl/pt8211_tx.v:14` 的 `BCK_HALF_PERIOD_CYCLES = 4'd15` 给出
32 拍一个 BCK，每立体声帧 32 个 BCK，合 1024 拍一个样本。
这是 PT8211 协议锁死的，不可改。

声部库、物理弦、加法合成、包络、混音、分配器这些逻辑，
**每 1024 拍才做一次有意义的工作**。让它们跑在 49 MHz 是不必要的。

54g 诊断报告中的四条最差路径：

```
uploaded_selected → status_bundle_cdc/src_payload_hold 的 CE   −3.219（线延迟 82.3%）
event_source      → event_glide_step                           −3.167（28 级逻辑）
timeline 批事件   → allocator_state                            −3.074
setting_key 消抖  → voice_releasing                            −3.052
```

**四条全部是每样本级或更慢的逻辑，没有一条需要每个时钟推进。**

## 三、方案

让音频引擎每两个 audio_clk 推进一拍，等效周期 40.69 ns，**采样率不变**。

```
audio_clk 49.15 MHz
  ├─ pt8211_tx          全速，1024 拍/帧，协议不变
  └─ 声部库及上游控制链  每两拍推进一次，等效 512 拍/样本
```

### 为什么不影响功能

| 项目 | 现状 | 方案后 |
|---|---|---|
| 采样率 | 48000.53 Hz | **不变** |
| 音高 / 音色 / 调音表 | — | **不变** |
| ADSR 时长 / 滑音 / 颤音 | — | **不变** |
| PT8211 帧结构 | 1024 拍 | **不变** |
| 声部库每样本可用拍数 | 1024 | 512 |
| 工程内最严时序契约 | 约 35 拍 | 仍为 35 拍 |

512 拍对 35 拍的需求，余量 14 倍以上。
工程内全部时序契约（stage29 共享波表 32 拍、第五刀共享音高乘法器 32 拍、
共享力度表 32 拍）均远小于 512。

## 四、实现方式（二选一，优先第一种）

### 方式 1：时钟使能（推荐）

不改 PLL、不新增时钟域、无 CDC 风险。

1. 在 audio_clk 域生成二分频脉冲 `half_tick`。
2. 声部库及其上游控制链的 always 块以 `if(half_tick)` 门控。
3. **`pt8211_tx` 不加门控**，保持全速。
4. **`audio_sample_strobe` 的产生不变**，它来自 `pt8211_tx`，
   但消费侧需确保 strobe 被 `half_tick` 正确采到，不得漏拍。
5. 配套 SDC 约束：对被门控的路径加
   `set_multicycle_path -setup 2` 与 `set_multicycle_path -hold 1`。

**`-hold 1` 不可省略。** 只写 setup 而不写 hold 会让工具按错误的
保持关系分析，可能引入实际的保持违例。

### 方式 2：独立时钟域

PLL 增加一路 24.576 MHz 输出。同源整数倍、相位固定，
但仍需处理跨域握手。**仅在方式 1 遇到实际阻碍时采用**，
并须说明阻碍是什么。

## 五、必须验证的项目

### 1. 采样率与协议（最高优先）

- 实测采样率仍为 48000.53 Hz。
- PT8211 帧结构不变：32 BCK/帧、1024 拍/样本、左右声道顺序与位宽不变。
- **不得只看 setup 数字变好就收工。** 必须有 PT8211 输出端的
  帧时序波形或逐拍断言作为证据。

### 2. 时序契约重新核算

原先按 1024 拍书写的契约，现在实际可用 512 拍。
**逐条确认仍满足，并更新 RTL 注释中的拍数与余量倍数。**
已知需核对的至少包括：

- `rtl/polyphony_bank_32.v:19, 297, 412, 456` 四处 1024 拍注释。
- stage29 共享钢琴波表的填充窗口。
- 第五刀共享音高乘法器的 32 拍轮询。
- 共享力度表的 32 拍刷新。

### 3. 负向用例按新拍数重跑

共享乘法器与共享力度表的负向用例，其"低于契约下限"的设定
需按 512 拍重新计算，确认仍能检出。

### 4. 完整回归

116 项全过、零失败。重点关注：

- 54 份音频 CSV 是否仍与基线一致。若有差异，必须逐项说明来源，
  不得以"半速化导致"一句带过。
- 两项引脚故障注入仍按预期检出。

### 5. 构建

一次 place3/route2 P&R，预算不低于 7200 秒。
读 setup、hold、违例数、CLS，以及 `.pr`、时序报告、`.fs` 是否齐全。

## 六、判定

- **setup 大幅转正**（预期进入正值且有可观余量）→ 方案成立，
  按既有门槛走完 45 引脚与时钟审计。
- **setup 仍为负** → 说明存在真正需要每个时钟推进的路径。
  **请报出这些路径，不要继续猜或自行扩大改动范围。**

## 七、风险与注意

1. **`set_multicycle_path` 写错会让工具放过真正的违例。**
   这是本方案最大的风险。必须同时写 setup 与 hold，
   并在报告中附上实际生效的约束内容（从 P&R 日志或 SDC 审计中读取），
   不能只声称"已添加"。
2. **`half_tick` 本身是高扇出控制信号。**
   它会分发到音频域大量 always 块。**不要对它施加 `syn_maxfan`**——
   stage29 对 `setting_mode`、stage33 对 `lane_allocate` 两次施加该属性
   均导致严重恶化（违例 22→750；布线停在 Routing Phase 0 无输出）。
   若 `half_tick` 成为新的关键路径，报出来再议。
3. **门控必须覆盖完整**。漏掉某个 always 块会造成该模块
   以两倍速率推进，与其余部分失步。
   建议按模块清单逐个确认，而非逐行搜索。
4. 保留 54g 全部证据，新尝试使用独立目录。

## 八、不得触碰

- 32 份独立相位累加器、32 份独立包络、8 条独立物理弦、32 个加法合成分量。
  72 个独立发声单元是赛题「同时活跃可闻独立振荡器总数」的计分依据。
- `pt8211_tx` 的分频常数与帧结构。
- 45 引脚约束、三个时钟的 `create_clock` / `create_generated_clock` 定义。
  本方案只增加 `set_multicycle_path`，不改时钟频率。
- 前五刀的资源收敛成果。

## 九、本方案不采用的替代路线及原因

- **降低 audio_clk 频率**：要补满 3.25 ns 需降约 14%，
  采样率将降至约 41.4 kHz，低于 44.1 kHz 且偏离赛题「48 kHz」要求 14%，
  答辩无法解释。小幅降频（2% 至 5%）只能换得 0.4 至 1.0 ns，不足以解决。
- **逐条拆解时序路径**：477 个违例、瓶颈随布局转移，
  每轮一次 P&R 约 20 分钟，时间上不可行。
- **分模式裁剪功能**：用户已明确要求一次位流实现全部功能，
  不接受测试版，不允许多次加载镜像。
